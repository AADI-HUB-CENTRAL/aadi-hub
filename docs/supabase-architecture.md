# AADI HUB — Supabase Architecture

> Companion to `supabase/migrations/20261016000001_init_schema.sql`.
> The migration is **prepared but NOT applied**. See `docs/setup-and-deployment.md`.

---

## 1. Why Supabase

The previous prototype had **no backend at all** — accounts, profiles and AADI
IDs lived in `localStorage`, so login was forgeable, passwords were discarded,
and a shared `/u/AADI-70001` link showed "Identity Unavailable" on every other
device.

Supabase gives us, in one vendor and on a free tier:

| Need | Supabase feature |
|---|---|
| Real signup / login / sessions | Supabase Auth (email+password, OAuth later) |
| Relational data | PostgreSQL |
| Authorization that cannot be bypassed from the browser | Row Level Security |
| Profile photos and covers | Storage, 5 MB per file |
| Unread-notification badge | Realtime (optional, added later) |

**No separate backend server is added.** The Vite SPA talks to Supabase
directly, and PostgreSQL RLS is the security boundary — not the React code.

## 2. Trust model

```
 Browser (React + supabase-js)
   │  anon/publishable key  ── public by design, safe in the bundle
   ▼
 Supabase REST (PostgREST)
   │  applies Row Level Security as the requesting user
   ▼
 PostgreSQL  ── RLS is the ONLY real access control
```

Rules that follow from this:

1. **The frontend is untrusted.** Any "guard" in React is UX only. Every table
   has RLS so a hand-crafted `fetch` to the REST API cannot do more than the
   policies allow.
2. **The service-role key never touches this repository.** It bypasses RLS
   entirely. It must only ever live in a server environment, and nothing in
   this project needs it.
3. **Only `VITE_`-prefixed, publishable values are used.** Vite inlines every
   `VITE_` variable into the public JS bundle. A secret in a `VITE_` variable
   is not a secret.
4. **No passwords in application tables.** Passwords are hashed by Supabase
   Auth inside `auth.users`. `profiles` deliberately has **no email column**,
   so a public profile can never leak an email address.

## 3. Identity model

| Concept | Source of truth |
|---|---|
| Authentication (email, password hash, verified_at, sessions) | `auth.users` |
| Public student identity | `public.profiles` |
| Display name at signup | `auth.users.raw_user_meta_data->>'full_name'`, copied into `profiles.full_name` by trigger |
| AADI ID | `public.profiles.aadi_id`, generated by the database |

A profile row is created automatically by the `on_auth_user_created` trigger on
`auth.users`. There is **no client path** that can create a profile with a
chosen AADI ID.

### AADI ID format and allocation

* Format: `AADI-` + zero-padded 5 digits, e.g. `AADI-80001`.
* Stored twice: `aadi_id` (text, unique, human-facing) and `aadi_id_num`
  (integer, unique, for ordering and range checks).
* Allocated by `public.allocate_aadi_id_num()`, a `SECURITY DEFINER` function
  that performs an atomic `UPDATE … RETURNING` on the single-row table
  `public.aadi_id_sequences`. Concurrent signups serialise on that row, so two
  users can never receive the same number.
* `allocate_aadi_id_num()` is `REVOKE`d from `public`, `anon` and
  `authenticated`. Only the signup trigger (running as `service_role`) can call it.

### Why the counter starts at 80001

The landing page (`src/components/Team.jsx`) advertises `AADI-70001`–`AADI-70004`
for the four founders. Those strings were **never written to any datastore** —
they are marketing content only — so there is nothing to migrate. Starting the
real counter at `80001` guarantees a genuine user can never collide with a
founder ID.

If real founder accounts are later created in Supabase, reserve their numbers
explicitly:

```sql
-- example, run by an administrator only
update public.aadi_id_sequences set last_num = 80004;
-- then create the four founder auth.users; they receive 80001..80004
```

### Immutable fields

`profiles_protect_fields` (a `BEFORE UPDATE` trigger) rejects any change to
`id`, `aadi_id`, `aadi_id_num` or `created_at`, and rejects a `role` change
unless the caller is a moderator/admin or is acting outside a user session.
So a user cannot promote themselves by calling
`PATCH /rest/v1/profiles?id=eq.<me>` with `{"role":"admin"}`.

## 4. Table catalogue

| Table | Purpose | Key relationships |
|---|---|---|
| `aadi_id_sequences` | Single-row counter for AADI IDs. No RLS policies at all. | — |
| `profiles` | Student identity. 1:1 with `auth.users`. **No email column.** Editable fields: `full_name`, `headline`, `bio`, `college`, `course`, `study_year`, `age_range`, `location`, `skills[]`, `interests[]`, `goals[]`, `roles[]`, `building`, `learning`, `exploring`, `looking_for`, `open_to`, `avatar_path`, `cover_type`, `cover_value`, `is_public`. | `id → auth.users(id)` |
| `projects` | A student's project showcase. `owner_id` is the source of truth for ownership. | `owner_id → profiles(id)` |
| `project_members` | Collaborators on a project. Owner is *not* duplicated here. | `(project_id, user_id)` PK |
| `communities` | Interest groups (AI Builders, Data Science, …). `member_count` is trigger-maintained. | `owner_id → profiles(id)` |
| `community_members` | Membership + role (`owner` / `moderator` / `member`). | `(community_id, user_id)` PK |
| `posts` | Feed entries — global (`community_id`/`project_id` NULL) or scoped. | `author_id → profiles(id)` |
| `comments` | Replies on a post. Deleting a post cascades. | `post_id → posts(id)` |
| `opportunities` | Internships, events, scholarships. **Only moderators/admins can create.** | `created_by → profiles(id)` |
| `challenges` | Daily / weekly / special build challenges. | `created_by → profiles(id)` |
| `challenge_participants` | Participation + submission. Composite PK **prevents duplicate joins**. | `(challenge_id, user_id)` PK |
| `notifications` | Per-user inbox. Only the recipient can read. | `user_id → profiles(id)` |
| `reports` | Abuse reports. Reporter sees own; moderators act. No delete policy. | `reporter_id → profiles(id)` |

Every table uses `on delete cascade` to `profiles` so deleting a user removes
their content, and `auth.users` → `profiles` cascade means deleting the auth
user removes everything.

## 5. Authorization model

### Role hierarchy

| Role | How granted | Can do |
|---|---|---|
| `student` (default) | Automatic on signup | Everything a normal member can |
| `moderator` | Set by an admin in SQL / dashboard | Moderate content, create opportunities & challenges |
| `admin` | Set by an admin in SQL / dashboard | All of the above + manage roles and communities |

`role` can only be changed by a moderator/admin (or outside a user session).
There is no self-service path to it.

### Ownership rules

| Resource | Owner can | Others can |
|---|---|---|
| Profile | Edit all editable fields, delete account | Read only if `is_public` |
| Project | Edit, delete, manage members, change visibility | Read if `visibility='public'` or they are a member |
| Community | Edit, delete, remove members, appoint moderators | Read if `is_public`; join if public |
| Post | Edit, delete | Read per scope; comment if they can read |
| Opportunity / Challenge | Edit, delete | Read only if `status='published'` / `status <> 'draft'` |
| Notification | Read, mark read, delete | Nobody else — no exceptions |
| Report | Read own, create | Moderators/admins can read and update status |

### The recursion trap (and how it is avoided)

A policy like this recurses infinitely in PostgreSQL, because checking the
policy requires evaluating the policy:

```sql
-- BROKEN
create policy ... on community_members
  for select using (exists (select 1 from community_members where ...));
```

Every cross-row check therefore goes through a `SECURITY DEFINER` helper with a
pinned `search_path`, which reads as the function owner and breaks the cycle:

```sql
public.is_admin()
public.is_project_owner(uuid)
public.is_project_member(uuid)
public.is_community_member(uuid)
public.has_community_role(uuid, text[])
```

All five are `REVOKE`d from `public`/`anon` and `GRANT`ed to `authenticated`.
They are safe to expose because they only ever return a boolean read from a
single indexed lookup, never write anything, and take an explicit target id
rather than trusting a client-supplied session value.

### Storage

One bucket, `profile-media`, used for avatars and custom covers.

* `public = true` → object URLs work in `<img src>` without signed URLs.
* `file_size_limit = 5242880` (5 MB), enforced by Storage, not by React.
* `allowed_mime_types = image/jpeg, image/png, image/webp`.
* Write path is `<auth.uid()>/<filename>`; policies compare
  `(storage.foldername(name))[1] = auth.uid()::text`, so a user can only write
  inside their own folder.

## 6. Deliberate product decisions (please confirm or change)

| # | Decision | Rationale | Where |
|---|---|---|---|
| 1 | **Profiles are publicly readable by default** (`is_public = true`) | A shareable portfolio at `/u/:aadiId` is the core AADI promise; the QR code on the ID card depends on it | `profiles.is_public` |
| 2 | **A private profile is invisible to everyone but its owner and moderators** | A real privacy switch, not a cosmetic toggle | `profiles_select_public` policy |
| 3 | **No email is stored in `profiles`** | A public profile can never leak an email address | schema |
| 4 | **Only moderators/admins can create opportunities** | Prevents the board being filled with fake internships by ordinary accounts | `opportunities_insert` policy |
| 5 | **Only moderators/admins can create challenges** | Same reasoning; challenges are a platform-curated activity | `challenges_insert` policy |
| 6 | **Users cannot promote themselves to winner / moderator** | `cp_update` restricts users to `joined`/`submitted`; role changes need `owner`/`moderator`/`admin` | RLS |
| 7 | **Notifications cannot be created for another user from the client** | Prevents spam. Cross-user notifications arrive later via a trusted function | `notifications_insert_own` |
| 8 | **Reports are never deleted** | Moderation retention | no delete policy on `reports` |
| 9 | **New AADI IDs start at `AADI-80001`** | Avoids collision with the 70001–70004 founder IDs shown on the landing page | `aadi_id_sequences` |
| 10 | **Onboarding is optional to complete but required to leave `/onboarding`** | Prevents redirect loops while still collecting a name | frontend guard |

## 7. Environment variables

| Name | Public? | Purpose |
|---|---|---|
| `VITE_SUPABASE_URL` | Yes | Project URL, e.g. `https://xxxx.supabase.co` |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Yes | The **anon / publishable** key. Safe in the bundle because RLS is the real gate. |
| `VITE_PUBLIC_APP_URL` | Yes | Canonical URL used to build password-reset / verification links |
| `VITE_FORMSPREE_ENDPOINT` | Yes | Existing early-access form (unchanged) |
| `VITE_WHATSAPP_COMMUNITY_URL` | Yes | Existing WhatsApp community link (unchanged) |

**Never add `VITE_SUPABASE_SERVICE_ROLE_KEY`.** It bypasses RLS. Nothing in this
frontend needs it, and Vite would publish it to every visitor.

## 8. What this architecture deliberately does NOT do

* No password reset / email verification **delivery** is verified here — that
  requires the Supabase dashboard configuration described in
  `docs/setup-and-deployment.md`.
* No payment system, no AI API, no separate server, no message queue.
* No realtime subscriptions yet. `notifications_unread_idx` is in place so a
  polling-based unread badge works today; Realtime can be switched on later
  without a schema change.
* No moderation queue UI yet — only the `reports` table and its policies.
